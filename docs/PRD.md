# Pulse — 个性化智能桌面行为分析助手 · 需求文档 v1.0

---

## 1. 项目概述

### 1.1 项目背景

Tai 是一款优秀的开源桌面应用使用统计工具，但其核心痛点在于**需要用户手动分类每个应用类型**，在应用数量庞大的场景下维护成本极高。进入大模型时代，应用分类完全可以由 AI 自动完成，用户只需对分类结果进行微调即可。

同时，现有的时间追踪工具普遍缺乏**行为层面的深度分析与预测**，也缺少与**日历/日程/健康**等生活维度的融合。Pulse 旨在打造一个以"应用使用统计"为基础，向上延伸至"行为理解 → 预测 → 生活整合"的个人化桌面助手。

### 1.2 项目定位

**个人向、个性化定制的桌面客户端**，核心解决三个问题：

| 层次 | 核心问题 | Pulse 的方案 |
|------|----------|-------------|
| L1 记录 | 我每天时间花在哪了？ | 自动追踪桌面应用使用，按天/周/月统计 |
| L2 理解 | 这些时间花得值不值？ | LLM 自动分类 + 行为模式分析 + 生产力评分 |
| L3 整合 | 我今天到底做了什么？ | 日历视图 + 自动生成每日总结 + 可选健康数据接入 |

### 1.3 技术栈

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 桌面框架 | PyQt6 | 跨平台桌面UI，成熟稳定 |
| 图表可视化 | pyqtgraph / QtCharts | 使用时长趋势图、饼图等 |
| 本地存储 | SQLite (SQLAlchemy ORM) | 轻量、无需额外部署 |
| LLM 集成 | OpenAI API / 本地 Ollama | 支持云端和本地两种模式 |
| 系统监控 | Windows API (pywin32/ctypes) | 窗口标题、进程名、活跃状态监控 |
| 健康数据 | Huawei Health Kit API (可选) | OAuth 2.0 接入 |

## 2. 用户画像与使用场景

### 2.1 目标用户

- 希望量化自我、提升时间管理能力的个人用户
- 自由职业者 / 远程办公者，需了解每日工作节奏
- 开发者、设计师等需要大量电脑时间的从业者
- 有运动习惯、希望将运动数据自动整合进日历的用户

### 2.2 典型使用场景

| 场景 | 描述 |
|------|------|
| 每日复盘 | 晚上打开 Pulse，查看今日各应用使用时长、分类占比、AI 生成的今日总结 |
| 周度回顾 | 周日查看本周 vs 上周的对比，发现时间分配变化趋势 |
| 应用分类 | 新装了一个软件，LLM 自动归类为"开发工具"，用户确认或手动调整 |
| 效率洞察 | Pulse 提示"你最近下午 2-4 点效率最高，建议安排核心工作" |
| 运动同步 | 跑步 5km 后，数据自动同步到 Pulse 日历，并在日记中显示 |
| 异常提醒 | 连续 3 天社交媒体使用超 2 小时，Pulse 主动提示 |

### 3.2 M1 — 应用追踪引擎

#### 3.2.1 功能描述
在后台静默运行，实时追踪当前活跃窗口的应用名称、窗口标题、活跃时长。

#### 3.2.2 详细需求

| 编号 | 需求 | 优先级 | 说明 |
|------|------|--------|------|
| M1-01 | 追踪活跃窗口 | P0 | 获取当前焦点窗口的进程名、窗口标题 |
| M1-02 | 记录使用时长 | P0 | 以秒为单位累加每个应用的使用时长 |
| M1-03 | 空闲检测 | P0 | N 分钟无键盘/鼠标操作判定为空闲，暂停计时 |
| M1-04 | 浏览器 URL 识别 | P1 | 对主流浏览器（Chrome/Edge/Firefox），从窗口标题提取域名或页面标题 |
| M1-05 | 数据聚合与存储 | P0 | 原始数据按分钟粒度存储，聚合数据按小时/天/周预计算 |
| M1-06 | 性能保护 | P0 | 采样频率默认 1 秒，CPU 占用 < 2%，内存 < 100MB |
| M1-07 | 隐私模式 | P1 | 一键暂停追踪，或对指定应用不记录 |

#### 3.2.3 数据结构

```
AppUsageRecord
├── id
├── timestamp          # 记录时间点（精确到秒）
├── process_name       # 进程名（如 "devenv.exe"）
├── window_title       # 窗口标题（如 "Pulse.py - PyCharm"）
├── duration_seconds   # 该记录持续的秒数
├── category_id        # 外键 → Category（可为空，待分类）
└── is_idle            # 是否为空闲时段
```

### 3.3 M2 — AI 智能分类

#### 3.3.1 功能描述
利用 LLM 根据进程名和窗口标题自动推断应用类别，支持用户自定义分类规则和手动覆盖。

#### 3.3.2 详细需求

| 编号 | 需求 | 优先级 | 说明 |
|------|------|--------|------|
| M2-01 | 自动分类 | P0 | 新出现未分类应用时，调用 LLM 推断类别 |
| M2-02 | 批量分类 | P0 | 对历史未分类数据，支持一键批量分类 |
| M2-03 | 自定义分类 | P0 | 用户可创建/编辑/删除分类，定义名称、颜色、图标 |
| M2-04 | 手动覆盖 | P0 | 用户可将已被自动分类的应用改为其他分类 |
| M2-05 | 规则固化 | P1 | 被用户手动修改过的应用，下次不再自动分类 |
| M2-06 | 分类继承 | P1 | 同类进程名（如不同版本）自动继承已有分类 |
| M2-07 | 本地 LLM 支持 | P1 | 支持通过 Ollama 本地运行，无需联网 |
| M2-08 | 分类缓存与去重 | P0 | 已分类的（进程名 + 分类）组合本地缓存，减少 LLM 调用 |

#### 3.3.3 预设分类体系

```
📁 开发与设计  → IDE、终端、设计工具、版本控制
📁 办公与效率  → 文档、邮件、笔记、日程
📁 浏览器      → 各类浏览器（URL级别可细分）
📁 社交与通讯  → 微信、QQ、钉钉、Telegram
📁 娱乐与影音  → 游戏、视频、音乐
📁 学习与阅读  → 电子书、在线课程、论文
📁 系统与工具  → 资源管理器、设置、终端工具
📁 其他        → 兜底分类
```

#### 3.3.4 LLM Prompt 设计要点

```
输入：进程名 + 窗口标题（可选）+ 预设分类列表
输出：JSON { category_id, confidence, reasoning }
要求：低延迟（< 2s），支持批量输入，分类一致性保证
```

### 3.5 M4 — 行为分析与预测

#### 3.5.1 功能描述
基于历史使用数据，分析用户行为模式，提供洞察，并对未来使用趋势进行预测。

#### 3.5.2 详细需求

| 编号 | 需求 | 优先级 | 说明 |
|------|------|--------|------|
| M4-01 | 生产力评分 | P1 | 基于自定义规则给每日打分（如开发时间占比、娱乐时间上限等） |
| M4-02 | 高峰期识别 | P1 | 分析一天中哪个时段用户最"专注"（长时间使用开发工具） |
| M4-03 | 使用模式聚类 | P2 | 识别"工作日模式" vs "周末模式" vs "异常日" |
| M4-04 | 趋势预测 | P2 | 基于历史数据预测明日/下周各分类使用时长 |
| M4-05 | 智能提醒 | P2 | 娱乐时长超过阈值时提醒、长时间未休息时提醒 |
| M4-06 | 周/月报告 | P2 | 自动生成文字版周报/月报，包含结论和改善建议 |

#### 3.5.3 行为模型输入特征

```python
# 用于分析/预测的特征向量
features = {
    "day_of_week": 0-6,           # 星期几
    "is_weekend": bool,           # 是否周末
    "hour_of_day": 0-23,          # 几点
    "prev_day_total": float,      # 昨日总时长
    "morning_ratio": float,       # 上午使用占比
    "category_distribution": {},  # 各类别分布
    "switch_frequency": int,      # 应用切换频率
    "idle_ratio": float,          # 空闲占比
}
```

### 3.6 M5 — 日历与日记

#### 3.6.1 功能描述
提供类似 Notion Calendar 的日历视图，自动将每日应用使用摘要和事件填入日历，支持手动添加日记/备注。

#### 3.6.2 详细需求

| 编号 | 需求 | 优先级 | 说明 |
|------|------|--------|------|
| M5-01 | 月历视图 | P1 | 标准月历，每日格子内显示简短摘要 |
| M5-02 | 日视图 | P1 | 点击某天，显示当日时间线 + 应用摘要 + 日记 |
| M5-03 | 周视图 | P2 | 7 天横向视图，适合规划 |
| M5-04 | 自动每日摘要 | P1 | AI 根据当日应用使用数据自动生成一句话总结 |
| M5-05 | 手动日记 | P1 | 支持纯文本/Markdown 写日记 |
| M5-06 | 事件标记 | P2 | 可手动添加事件（如"会议 14:00-15:00"） |
| M5-07 | 应用时段关联 | P2 | 日记中自动关联"这段时间你在用什么应用" |

#### 3.6.3 日历数据结构

```
CalendarEntry
├── id
├── date                     # 日期
├── entry_type               # ENUM: auto_summary, manual_journal, event, health_data
├── title
├── content                  # Markdown 内容
├── start_time / end_time    # 时间段（可选，事件类型）
├── source                   # 数据来源：system / manual / huawei_health
└── created_at / updated_at
```

#### 3.6.4 自动摘要 Prompt 示例

```

- 开发工具：3h45m（PyCharm 3h, VSCode 45m）
- 浏览器：2h10m（查阅文档、GitHub、Stack Overflow）

│ │      │  │     内容区域                  │ │

## 4. 非功能性需求

| 类别 | 要求 |
|------|------|
| 性能 | 后台监控 CPU < 2%，内存 < 100MB，UI 响应 < 200ms |
| 数据安全 | 所有数据本地存储，不上传任何使用数据到云端（除非用户主动选择云同步） |
| 隐私 | LLM 调用仅发送进程名/窗口标题，不发送具体内容 |
| 可用性 | 安装即用，首次启动引导流程不超过 3 步 |
| 可扩展性 | 插件化架构，健康接入模块可独立启用/禁用 |
| 兼容性 | 优先支持 Windows 10/11，预留 macOS 扩展可能 |

│  ┌──────────┐ ┌──────────┐ ┌─────────────┐  │

```

### 5.2 核心数据流

```
Windows窗口事件 → 追踪服务 → 原始记录(SQLite)
                                ↓
                      分类服务(LLM) → 分类结果
                                ↓
                      聚合服务 → 按小时/天聚合
                                ↓
                    ┌───────────┴───────────┐
                    ↓                       ↓
              统计看板(UI)         行为分析引擎
                                          ↓
                                   预测/建议/报告
                                          ↓
                                   日历 + 日记
                                          ↑
                                 华为健康 API (可选)
```

## 7. 待讨论与决策点

| # | 议题 | 选项 | 建议 |
|---|------|------|------|
| 1 | LLM 默认方案 | OpenAI API vs 本地 Ollama | MVP 先用 OpenAI API（零部署成本），后续加 Ollama |
| 2 | 窗口追踪技术 | pywin32 vs psutil vs uiautomation | 建议 pywin32 获取窗口标题 + psutil 获取进程名 |
| 3 | UI 框架 | PyQt6 vs PySide6 | 已选 PyQt6，已实现 |
| 4 | 图表库 | pyqtgraph vs matplotlib vs QtCharts | pyqtgraph 性能好，原生 Qt 集成佳 |
| 5 | 数据存储 | SQLite vs DuckDB | SQLite 够用，DuckDB 对分析查询有优势但引入额外依赖 |
| 6 | 自动摘要 AI | 复用 LLM 客户端 vs 本地小模型 | 复用 LLM 客户端即可，摘要不是高频操作 |
| 7 | 浏览器URL识别 | URL 提取插件 vs 浏览器扩展 | 先用窗口标题正则提取域名，后续可做浏览器扩展 |
